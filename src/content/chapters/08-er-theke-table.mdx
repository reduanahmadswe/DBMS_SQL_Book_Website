## সমস্যাটা আসলে কী

ER ডায়াগ্রাম ধারণাগত; DBMS বোঝে টেবিল। ER-এর প্রতিটি নির্মাণ (entity, attribute, relationship, weak entity, specialization…) টেবিল-কলাম-key-তে কীভাবে যাবে, এই স্পষ্ট ধাপগুলোই ER-to-relational mapping (Elmasri & Navathe-এর অ্যালগরিদম)।

## কদম চাচার ক্লাস: ধাপে ধাপে নিয়ম

### ধাপ ১: Regular (strong) entity

প্রতিটি entity set → একটি টেবিল। Simple attribute → কলাম। Composite → উপাদানগুলো আলাদা কলাম। Key → primary key।

| ER | টেবিল |
|---|---|
| `Customer(customer_id, name, phone, address(area, city), email)` | `customers(customer_id PK, name, phone, area, city, email)` |

### ধাপ ২: Weak entity

নতুন টেবিল; owner-এর primary key এখানে foreign key হিসেবে আসে; owner-key + partial key মিলে primary key।

### ধাপ ৩: Binary 1:1

তিনটি পদ্ধতি: (ক) Foreign key পদ্ধতি (সবচেয়ে প্রচলিত), একদিকের টেবিলে অপর দিকের key FK হিসেবে রেখে `UNIQUE` করা; total participation-এর দিকে রাখাই ভালো (NULL এড়াতে)। (খ) Merged relation, দুই entity যদি দুদিকেই total হয়, এক টেবিলে মিলিয়ে ফেলা। (গ) Cross-reference (relationship টেবিল), দুই key ও সম্পর্কের attribute নিয়ে আলাদা টেবিল (দুদিকেই partial হলে)।

আমাদের `deliveries.order_id UNIQUE`, প্রতিটি delivery একটি অর্ডারের, প্রতিটি অর্ডারের একটি delivery।

### ধাপ ৪: Binary 1:N

N-দিকের টেবিলে 1-দিকের primary key foreign key হিসেবে। সম্পর্কের নিজস্ব attribute N-দিকের টেবিলে যায়।

| ER | টেবিল |
|---|---|
| Customer 1, places, N Order | `orders(order_id PK, customer_id FK → customers, …)` |

### ধাপ ৫: Binary M:N

নতুন সংযোগ-টেবিল (relationship/junction/associative table): দুই entity-র primary key দুটি FK, মিলে composite primary key; সম্পর্কের attribute-ও এখানে।

| ER | টেবিল |
|---|---|
| Order M, contains, N Product (quantity) | `order_items(order_id FK, product_id FK, quantity, unit_price, PK(order_id, product_id))` |

### ধাপ ৬: Multi-valued attribute

নতুন টেবিল: entity-র key (FK) + attribute; দুটি মিলে PK।

| ER | টেবিল |
|---|---|
| `Supplier.phone` (multi-valued) | `supplier_phones(supplier_id FK, phone, PK(supplier_id, phone))` |

### ধাপ ৭: N-ary (ternary) সম্পর্ক

নতুন টেবিল; প্রতিটি জড়িত entity-র key FK; PK সাধারণত সবকটির সমন্বয় (কার্ডিনালিটি অনুযায়ী ছোট হতে পারে); সম্পর্কের attribute যুক্ত।

`supplies(supplier_id FK, product_id FK, store_id FK, quantity, supply_date, PK(supplier_id, product_id, store_id))`।

### Unary (recursive) সম্পর্ক

1:N unary → একই টেবিলে নিজের key-কে refer করা FK: `employees.manager_id → employees.employee_id`। M:N unary → আলাদা সংযোগ-টেবিল (দুটি কলাম একই টেবিলের key)।

### Derived attribute

কলাম বানানো হয় না; কোয়েরি বা view-তে হিসাব।

### EER: Specialization/Generalization

চারটি বিকল্প (Navathe 8A–8D):

| বিকল্প | কখন | গঠন |
|---|---|---|
| **৮A: সুপারক্লাস + প্রতিটি সাবক্লাস আলাদা টেবিল** | সব ক্ষেত্রে (disjoint/overlapping, total/partial) | সাবক্লাস টেবিলের PK = সুপারক্লাসের PK (একই সাথে FK) |
| **৮B: শুধু সাবক্লাস টেবিল** | total + disjoint | প্রতিটি সাবক্লাসে সুপারক্লাসের সব attribute |
| **৮C: একটি টেবিল + type কলাম** | disjoint | সব attribute এক টেবিলে; `emp_type` কলাম; অপ্রযোজ্যগুলো NULL |
| **৮D: একটি টেবিল + একাধিক boolean কলাম** | overlapping | `is_rider`, `is_manager`… ফ্ল্যাগ |

### Category (Union)

সাধারণত একটি surrogate key দিয়ে `payers(payer_id PK, …)` টেবিল; superclass-গুলোর টেবিলে `payer_id` FK যোগ। (Superclass-গুলোর key ভিন্ন ধরনের হলে surrogate অপরিহার্য।)

### Aggregation

সম্পর্ক-টেবিলটিকেই (`deliveries(order_id, rider_id)`) একটি entity-র মতো ধরে নতুন সম্পর্ক-টেবিলে সেটির PK-কে FK বানাও।

## টেকনিক্যাল গভীরে: ক্লাসিক পরীক্ষার ERD

পরীক্ষার প্রশ্ন সাধারণত: "নিচের বর্ণনা থেকে ERD আঁকো ও টেবিলে রূপান্তর করো।" ছয়টি ক্লাসিক সমাধানসহ।

### ১. University

বর্ণনা: প্রতিটি ছাত্র একটি বিভাগে পড়ে; বিভাগে অনেক শিক্ষক; প্রতিটি কোর্স একজন শিক্ষক পড়ান; ছাত্র অনেক কোর্সে ভর্তি হয়, কোর্সে অনেক ছাত্র; ভর্তিতে grade থাকে।

- **M:N-কে FK দিয়ে ম্যাপ করা**: সবসময় সংযোগ-টেবিল।
- **Weak entity-র PK-তে owner-key ভুলে যাওয়া**।
- **Multi-valued attribute কমা-বিভক্ত কলামে রাখা**।
- **1:N-এ FK ভুল পাশে রাখা**: FK সবসময় **N-দিকে** (বহু-র দিকে)।
- **Derived attribute কলাম বানানো**।

## পরীক্ষার টিপস

<Callout type="exam">
লিখিত: ER থেকে টেবিলে রূপান্তরের ধাপ (৭ ধাপ) তালিকা + ছোট উদাহরণ, প্রায় নিশ্চিত প্রশ্ন। ERD আঁকার প্রশ্নে *তিনটি* জিনিস দেখাও: ERD → টেবিল-স্কিমা (PK/FK চিহ্নিত) → বিবৃতি অনুযায়ী কার্ডিনালিটির যুক্তি। MCQ ট্র্যাপ: (১) 1:N-এ FK N-দিকে। (২) M:N-এ composite PK। (৩) n টেবিল ও m সংযোগ-টেবিল: "মোট টেবিল কয়টি" ধরনের গণনা, প্রতিটি entity + প্রতিটি M:N + প্রতিটি multi-valued attribute।
</Callout>

<Summary>
- Regular entity → টেবিল; composite → কলাম ভেঙে; derived → কলাম নয়।
- Weak entity → টেবিল, PK = owner key + partial key।
- 1:1 → একদিকে FK + UNIQUE; 1:N → N-দিকে FK; M:N → সংযোগ-টেবিল; multi-valued → আলাদা টেবিল; n-ary → সব key নিয়ে টেবিল।
- Specialization-এর চার বিকল্প (৮A–৮D); category → surrogate key।
- চূড়ান্ত `ledu_mart` ১১ টেবিল, এই নিয়মেই ER থেকে এসেছে।
</Summary>

<Exercise n={1}>
ER: `Student M, enrolls, N Course` (attribute: `grade`)। রিলেশনাল স্কিমা লেখো।

<Answer>
`student(student_id PK, …)`, `course(course_code PK, …)`, `enrollment(student_id FK, course_code FK, grade, PK(student_id, course_code))`।
</Answer>
</Exercise>

<Exercise n={2}>
`Rider 1, rides, 1 Bike` (Rider total participation)। কোন টেবিলে FK রাখবে?

<Answer>
Total participation-এর দিকে, অর্থাৎ `rider` টেবিলে `bike_no FK UNIQUE NOT NULL`, যাতে NULL এড়ানো যায়। (বিকল্প: bike-এ `rider_id FK UNIQUE`, তখন যে বাইকের রাইডার নেই তার জন্য NULL।)
</Answer>
</Exercise>

<Exercise n={3}>
`order_items`-এর সাথে `products` জোড়া দিয়ে অর্ডার #২-এর পণ্যের নাম ও পরিমাণ দেখাও।

<Answer>
```sql
SELECT p.name, oi.quantity
FROM order_items oi
JOIN products p ON p.product_id = oi.product_id
WHERE oi.order_id = 2;
```
</Answer>
</Exercise>

<Exercise n={4}>
মোট কয়টি টেবিল লাগবে: এন্টিটি `A`, `B`, `C`; সম্পর্ক `A M:N B`, `B 1:N C`; `A`-এর একটি multi-valued attribute?

<Answer>
৩ (entity) + ১ (A–B সংযোগ-টেবিল) + ১ (multi-valued) = ৫টি। B–C সম্পর্ক 1:N তাই `C`-তে FK; নতুন টেবিল লাগে না।
</Answer>
</Exercise>
